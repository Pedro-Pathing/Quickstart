Read this first

↑ contents

This repository is a complete robot program, and almost none of the robot's behavior is hard-coded in Java. It comes from one YAML file. Making the robot work takes three steps: install the app, run the calibration OpModes on the real robot (each one prints numbers), and paste those numbers into config.yaml. Then you run the automated checks and the on-robot acceptance tests.

!
As of this snapshot the robot is safe but will not score. These values still have to be replaced:
  • shooter.shot_table.calibrated: false. The shot rows are invented, and no ball is ever fed (not in AUTO, TeleOp, or the D-pad Up fixed shot) until you run Ballistics Calibration and set this to true.
  • auto.shot_time_points has 2 placeholder rows. Run Shot Timing Tuner.
  • vision.camera.* is unmeasured, so HIVE tracking and relocalization will be wrong until it is measured.
  • pedro.* is carried over from last season. The migration notes call the gains, feedforward and braking provisional, and max_forward_velocity is flagged "recheck on robot".
  • turret.kv: 0 (no chassis feedforward), turret.pivot_*_in: 0 (unmeasured), shooter.kick.wheel_tau_sec: 0 (recovery kick off), inventory.entry_sensor_enabled: false (no ball counter).
✓
The golden rules
  1. Never edit config.java or config-schema.json. Both are generated.
  2. Numbers go in config.yaml, descriptions in config-docs.yaml. Then run ./gradlew verifyBuild.
  3. Write poses for RED only. BLUE is the letter m (RED rotated 180° about the field centre).
  4. Never bypass Sentinel/Casablanca. They keep the robot off the HIVE frame (ramming it is a foul, G417).
  5. Test slowly. Anything that spins goes on blocks first.

The five-minute mental model

Drivetrain + odometry

4 mecanum wheels. A goBILDA Pinpoint with two odometry pods tracks where the robot is. Pedro Pathing follows paths using that position.

Intake

Two motors (front and middle rollers) pull POLLEN in and pass it to the shooter. It caps itself at 4 elements only if a beam break is fitted.

Shooter

Two motors drive one flywheel, and a hood servo sets the launch angle. A measured shot table maps distance to (hood, flywheel speed).

Turret

A continuous-rotation servo swings the shooter about ±26°. An analog potentiometer reads the angle. It aims at the upward CELL on its own.

Vision

A webcam reads AprilTags under each CELL. Their height tells it which CELL faces up, and so whether the HIVE has TIPPED.

Safety layer

Sentinel knows the no-go zones (JTS polygons). Casablanca slows and pushes back driver input near them, and holds heading.

Shot controller

Feeds a ball only when every gate passes: flywheel in band, turret aligned, solution valid and current, HIVE settled.

Config

One YAML file holds every constant. It can be hot-pushed over ADB in seconds without rebuilding the app.

Proofs + tests

JVM tests simulate turret and flywheel physics and check every auto route. OpenJML and Lean proofs cover the turret and feed logic.

Getting code onto the robot

↑ contents

4.1 One-time setup

  1. Install Android Studio and a JDK 21 (the build targets Java 21).
  2. Open the repo root (the folder containing gradlew) and let Gradle sync. The robot code is the TeamCode module.
  3. Make sure adb exists. The build looks in $ANDROID_HOME, $ANDROID_SDK_ROOT, then ~/Library/Android/sdk/platform-tools.
  4. Optional (proofs): install Lean with brew install elan-init. The first verifyBuild then runs setupOpenJml and setupLean, which download OpenJML and about 5 GB of Mathlib once.

4.2 Connect to the Control Hub

Wi-Fi (default). Join the robot's Wi-Fi. The hub is at 192.168.43.1:5555.

./gradlew connectAdb
./gradlew connectAdb -PadbAddress=192.168.43.1:5555  # explicit
adb devices          # lists the hub

USB. Use a USB-A to USB-C cable (REV's standard). On this team's MacBook a C-to-C cable never came up, because the hub took the host role. Use an A-to-C cable or a C-to-A adapter.

!
macOS: "No route to host" while you are on the robot Wi-Fi usually means macOS is blocking local-network access for your terminal. Allow it in System Settings › Privacy & Security › Local Network.

4.3 Build and install

  1. Prove the code is healthy, no robot needed: 
    ./gradlew verifyBuild
    This formats, compiles, runs every unit test, checks red_*/blue_* symmetry and runs the proofs. It must pass (§8.1).
  2. Install: in Android Studio pick the TeamCode run configuration, choose the hub as the device, and press ▶ Run. The CLI equivalent is the standard Android task ./gradlew :TeamCode:installDebug.
  3. On the DS you should see TeleOp, the six autos (Red/Blue A: tip first, Red/Blue B: second CELL, Red/Blue Park Only) and the tuning OpModes.
i
Gradle prints nothing for over a minute? The daemon is probably frozen (ps shows state T). Re-run with ./gradlew --no-daemon <task>.

4.4 Hot-push config: the tuning loop

While tuning, you change numbers dozens of times. Push the config file instead of rebuilding the app:

Editconfig.yaml
›
Push./gradlew pushConfig
›
Re-INITstop, then INIT the OpMode again
›
Testwatch telemetry
›
Lock incommit, verifyBuild, reinstall, resetConfig
CommandWhat it does
./gradlew pushConfigFirst runs checkPushConfig (autonomous-route safety, the shipped-config ConfigSanity check and match windows, under ½ s), then copies the file to /sdcard/FIRST/teamcode/config.yaml over ADB. A value-only change recompiles nothing. Re-INIT the OpMode to load it.
./gradlew resetConfigDeletes that override file, so the robot reverts to the config bundled in the APK.
./gradlew generateConfigRegenerates config.java and config-schema.json after you add a key. verifyBuild runs it too.
!
The robot uses a pushed file only if its meta.season is "biobuzz". Otherwise the DS shows why it was ignored. A plain adb push skips the safety check, and the robot never re-checks autonomous routes itself. Before competition, copy the final values into the repo, run verifyBuild, reinstall, then resetConfig, so there is exactly one source of truth.

4.5 Getting files off the robot

Calibration OpModes write their results to /sdcard/FIRST/teamcode/ on the hub. Pull them into calibration-data/ to keep a record. Each file is overwritten on the next run, so pull it before re-running.

adb pull /sdcard/FIRST/teamcode/shot_table_pollen.yaml calibration-data/
adb pull /sdcard/FIRST/teamcode/shot_time_table.yaml   calibration-data/
adb pull /sdcard/FIRST/teamcode/shot_timing_log.csv    calibration-data/
adb pull /sdcard/FIRST/teamcode/shooter_characterization.json calibration-data/

How configuration works

↑ contents
  • One file, robot/config/config.yaml, holds every tunable. config-docs.yaml holds each key's description and its min/max, keyed by the leaf name (e.g. kv).
  • Java reads values through a generated typed class, for example config.turret.pidf.p. No numbers are hard-coded.
  • Adding a key: add it to the YAML, add a desc (and min/max) to the docs file, then run generateConfig. A value outside min/max fails the build.
  • Alliances: a red_* key without a blue_* twin fails checkConfigKeys. Poses are RED plus m. If BLUE measures differently, replace that m with explicit numbers.
  • Season tag meta.season: "biobuzz" stays fixed for the whole season. It makes the robot ignore a leftover pushed config from another game.
  • At INIT, every tuning OpMode shows config problems on the DS: a rejected push, a broken shot table, a bad encoder range, and so on. Read the top of the telemetry.

7.2 Drivetrain: Pedro AutoTune writes pedro.*

Pedro AutoTune proceduresbrowser page on the hubneeds 4+ ft clearwheels on floor
Steps
  1. Connect a laptop to the robot's Wi-Fi and open http://192.168.43.1:10158.
  2. Mecanum Tuner spins each drive motor in turn, and you enter whether it went forward or reversed. This sets the motor directions.
  3. Pinpoint Tuner: pick the pod type, then push the robot forward exactly 48 in (encoder scale), then push it forward and then left (pod directions).
  4. Foresight Tuner: drives itself (48 in by default, and at least 15 in for braking) to measure heading kP, braking coefficients, top speeds and natural deceleration.
  5. Tests: Hold, Line, Curve, Interpolation, Localization, Odometry, Driving, Pose. Run Localization and Line first.
  6. Copy the reported numbers into config.yaml under pedro: (§10.1), then pushConfig. Each procedure reloads config, so no restart is needed.
Then verify
  • Forward Left Return Test (Autonomous, group Tests): from where it stands, it drives 20 in forward, 10 in left, then back. It should end where it started. The DS shows the live pose.
  • Push the robot by hand at heading 0. Forward must raise x, left must raise y, and turning counter-clockwise must raise the heading.
Watch out
  • max_forward_velocity: 79.97 is flagged in the file as unusually low.
  • After a chassis change, redo all four procedures, then §7.3, because Casablanca reuses pedro.braking.

7.3 Driver feel and safety (Casablanca) writes casablanca.*

Friction Calibration TeleOpCalibrationopen carpet~4 ft clearPanels thresholds
What it does

It slowly ramps power until the robot actually moves (above 1 in/s, or 0.05 rad/s for rotation, held for 5 loops). That gives the static-friction power on each axis. The rotation test also measures friction while already moving and the top rotation rate.

Controls
  • A forward test → kS X
  • B strafe test → kS Y
  • X rotation test → static, moving, max ω
casablanca.friction.x ← X · .y ← Y · .rot ← Rot Static
casablanca.heading_lock.ks_moving ← Rot Moving (keep the old value if it says NOT MEASURED)
sentinel.rotation_lookahead_time ← "Suggested rotation_lookahead_time" (0.45 / max ω)
Casablanca Pod Contact TunerCalibrationone axis per run48 in lane both ways
Why

The odometry pods ride on small spring mounts. Hard acceleration or braking can lift a pod off the floor and corrupt the robot's position. This finds the gentlest power slew limits that keep both pods in contact.

Steps
  1. Set casablanca.jump_tuner.trial_axis to FORWARD, STRAFE or TURN, then push and INIT.
  2. Place the robot at jump_tuner.calibration_pose = [20, 72, 90], a lane beside the HIVE. STRAFE trials start there turned 90°.
  3. Hold A for each trial: baseline, accelerate, hold, stop, settle. There is no automatic return, so reposition by hand between trials.
  4. Repeat until it shows a recommendation. Do the other axes the same way.
Controls
  • A hold = run trial (keep holding through the stop)
  • X mark "pod lifted" (you saw it lift)
  • release A / B / STOP = abort now
Output
casablanca.smoothing.<axis>.increase_time
casablanca.smoothing.<axis>.decrease_time

It aborts on more than 10° of tilt, a stale IMU, a stall, or drift. All limits are in casablanca.jump_tuner.*.

TeleOp Heading Lock AutotunerCalibrationturns in place
Steps
  1. Place the robot at heading_tuner.calibration_pose = [20, 72, 90] with room to turn.
  2. Press START, then hold A for the whole search. It steps the heading ±10° for every (P, D) pair: P from 1 to 10 in 4 steps, D from 0 to 0.9 in 4 steps.
  3. It keeps the pair with the best worst-case settling time that passes in both directions.
Controls
  • A hold = search · release A or press B = abort
Output
casablanca.heading_lock.pid.p ← p
casablanca.heading_lock.pid.d ← d (i stays 0)

heading_tolerance_degrees must be at least heading_lock.error_deadband_deg, or it refuses to start.

Casablanca TestTest · verifydrives as BLUEPanels field view

This is normal TeleOp driving through Casablanca (cubic sticks, slow-down, repulsion, heading lock), with live telemetry. It drives as BLUE and starts at the BLUE image of the tuner pose, (121.5, 69.5, 270°), so place the robot there. Drive at the HIVE frame from the front, side and diagonals at full speed. It must start slowing about 8 in out (slow_down), cut power toward the frame about 2.5 in out (hard_stop), and never touch.

Panels toggles
  • rawDirectDrive: bypass Casablanca to compare

Creeps in: raise hard_stop, check sentinel.robot_width and pedro.braking. Feels sluggish: lower slow_down. Keep depth and side symmetric.

7.4 Turret writes turret.* · do the cards in order

① Turret Center CalibrationTuningservo unpoweredby handPanels margin
Steps
  1. Turn the turret by hand to the positive hard stop and press A.
  2. Turn it to the negative hard stop and press A.
  3. Turn it to roughly the middle and press A. This only tells it which of the potentiometer's two arcs the turret travels. The exact centre is computed from the stops.
  4. B starts over. Paste the printed block.

The travel limits are half the measured span minus limitSafetyMarginDeg (3°) Panels. It keeps the existing degrees_per_volt unless you set knownTotalTravelDeg Panels to re-derive it.

Output (paste)
turret:
  travel: { min_angle, max_angle }
  analog_encoder:
    zero_voltage, degrees_per_volt,
    min_voltage, max_voltage,
    full_scale_voltage
② Turret Plant CalibrationTuningturret moves itselfPanels τ
Why not normal autotuning

A CR servo is an integrator: power sets speed, not position, so relay autotuning gives meaningless gains. This OpMode measures the breakaway power in each direction (kS) and the speed per unit of power (K). Then it picks p = 1/(K·τ) for a closed-loop time constant τ = desiredTimeConstantSec (0.20 s) Panels.

Steps
  1. Press START. The turret ramps power on its own within its travel limits, up to max_power_output. B aborts at any time.
  2. If it reports CONTROL LOOP IS INVERTED, flip turret.servo_direction_inverted and re-run before using any closed-loop OpMode.
  3. Paste the block.
Output (paste)
turret:
  ks_positive: …  ks_negative: …
  kv: … # 1/K, enables feedforward
  pidf: { p: …, i: 0, d: 0, f: 0 }
!
The convergence proof assumes i = d = f = 0, and the repo currently has i: 0.008. After any turret gain change, run
python3 TeamCode/verification/TurretProof/conditions.py
It must exit 0, and it prints the target distances the proof covers.
③ Turret Angle VerificationTuningneeds turnImu

Compares the encoder angle against an independent IMU mounted on the turret (turnImu, oriented by turret.orientation.logo/usb). After each move, the encoder and IMU angles should agree within about 1°. A consistent scale error means degrees_per_volt is off. It also warns at INIT if a pushed zero_voltage would put the encoder's wrap point inside the travel.

Then measure by hand
  • turret.pivot_forward_in, pivot_left_in: the turret axis position from the robot centre. A 4 in error is a 6–9° aim error at BIOBUZZ ranges.
  • The lopsided kS (+0.0009 / −0.0663) suggests the servo's neutral is about 0.033 off centre. Re-centre it with a servo programmer, then re-run ②.
Controls
  • D↑/D↓ target ±5° · D←/D→ ±15°
  • Y 0° · X +30° · B −30° (clamped to travel)
  • A zero IMU reference
  • LT kill power / idle · RB clear safety fault

7.5 Flywheel and hood writes shooter.*

Shooter CharacterizationCalibration~30 sflywheel clear of ballsbattery under load
Steps
  1. Press START, then A. It holds a staircase of open-loop powers, waits for the wheel to settle at each, and least-squares fits power = kV·speed + kS. Each point is corrected from the measured battery voltage to shooter.nominal_voltage.
  2. Then it steps the power from 0.40 to 0.85 and fits the wheel's time constant and the speed sensor's delay.
  3. Check the fit's RMS and worst error, which it shows on screen, then paste. A copy is saved as shooter_characterization.json.

If use_ftc_pid is true, the screen warns you that these values are ignored. p = 2·kV (loop gain 2) and i = p / 2 s were chosen by simulation sweep and are checked by FlywheelClosedLoopProperties.

Output (paste under shooter:)
ks: …
pidf: { p: …, i: …, d: 0, f: … }
kick: # only if the step test passed
  wheel_tau_sec: …

A non-zero wheel_tau_sec turns on the recovery kick. After a ball (or during spin-up), it applies as much power as the wheel model allows without overshooting, until the speed is predicted to reach the feed band. If the step test fails, it says so. Leave kick alone in that case.

Three things that bite after calibrating.
  1. Range. A shot is valid only inside the table's distances and inside min_valid_distance–max_valid_distance (24–72). With a 24–48 in table, the robot will not shoot from 50 in. To shoot farther, calibrate along a longer ray.

9.1 Pre-match checklist

  1. Charged battery. Connect the hub and the DS. INIT shows no config warning (ignored override, shot-table error, uncalibrated table).
  2. Agree on autos with your partner: one A: tip first and one B: second CELL, or Park Only. Pick the right alliance's OpMode. Each AUTO preselects TeleOp.
  3. Place the robot on its start pose: touching the wall, wholly on your side, not in the LOADING ZONE, not touching a FLOWER.
  4. Load exactly 4 POLLEN (inventory.preload_count).
  5. INIT, then START. Don't touch the robot in between.
  6. Start TeleOp within 2 minutes of AUTO so it inherits alliance, pose, HIVE state and inventory. Without an AUTO it defaults to RED. Press B (RED) or X (BLUE) on either gamepad during INIT.

Known gaps and further reading

↑ contents

Not built, or limited

  • No FLOWER mechanism. All three flower switches are off, so each auto fires only its 4 pre-loads.
  • No NECTAR mechanism. Every shot uses the POLLEN table.
  • No color sensor. The operator ejects opponent NECTAR (G408).
  • Continuous feeding while every gate passes. A TIP detected mid-volley stops further feeding, but balls already in the air can't be recalled.
  • Hood settling is not measured: the servo readback is just the command. A clamped speed is not re-validated against the table.
  • Moving shots use first-order lead only, with a conservative 20 in/s limit.
  • Hood range. A launch-model estimate wants a 64–78° lob, and the hood tops out at 65°. Confirm the real mechanism scores at 24–48 in.
  • Calibration reach. Both calibration OpModes stop at 48 in (the ray ends around 52 in), so longer shots need a different ray.
  • Proof scope. The proofs cover the control logic for a stated plant model and the conditions conditions.py checks. They don't show the hardware matches the model. §8.3 does.
  • Unused hardware. The gate servo appears in hwmap.yaml, but no code drives it.
